# Процесс «Запас»

## 0. Перед работой (каждая сессия)
1. Прочитай `AGENTS.md` (красные линии), `docs/ROLES.md` (найди свою зону), `docs/MEMORY.md` (подводные камни).
2. `git fetch --prune origin`. На `main` — `git pull --ff-only`; на своей активной ветке — `git rebase origin/main` с чистым working tree.
3. Найди задачу в `docs/TASKS.md` и требование в `docs/REQUIREMENTS.md` по ID. Без ID не начинай — спроси человека.

## 1. Взять задачу
```bash
git switch -c feat/FR-LED-11-recurring-detector
# параллельная задача: git worktree add ../zapas-FR-LED-11 -b feat/FR-LED-11-recurring-detector
```
Сразу открой draft PR (`gh pr create --draft --fill`) и поставь в `TASKS.md` статус `doing #<PR>` — это «я взял».

## 2. Контракт прежде кода
- Нужен новый эндпоинт/поле → отдельный PR `contract/<ID>-...` только в `contracts/**`, ревью владельца и потребителей (скилл `contracts-first`).
- До слияния контракта клиенты работают на моках: `pnpm contracts:mock`.
- Не правь чужую зону. Нужно изменение у соседа — опиши в комментарии PR или issue с меткой его зоны.

## 3. Пиши маленькими шагами
- `git var GIT_AUTHOR_IDENT`: author name/email должны принадлежать твоему человеку, связанному GitHub-аккаунту. PR публикуется тем же аккаунтом. Не impersonate соседа, не добавляй AI/agent/generator footer или Co-authored-by. Пользователь отвечает за изменение, текст commit/PR только о коде/контракте/проверках. Названия Jev/LLM как функции продукта допустимы.
- Сначала тест на поведение (скилл `test-driven-development`), потом код.
- Коммит каждые 20–40 минут: `feat(ledger): FR-LED-11 группировка по контрагенту`. commitlint проверит формат.
- Комментарии — только «почему». Никаких TODO в коде — заведи задачу.

## 4. Проверки (то же, что CI)
```bash
node tools/check.mjs <зона>     # web | admin | ui | backend:<svc> | ml | android | contracts
node tools/check.mjs changed    # всё, что ты затронул
```
Если упало — чини причину (скилл `systematic-debugging`), не отключай проверку.

## 5. PR
- Заполни шаблон: что сделано, **как проверить руками**, **как это работает (3–5 строк для защиты)**, риски.
- Перед «готово»: скилл `verification-before-completion` — запусти проверки и проверь поведение руками (UI или `.http`).
- PR ≤ ~400 строк без сгенерированных. Больше — разбей.
- Ревью: попроси человека открыть свежую сессию с ролью «ревьюер». Агент **не апрувит и не мёржит**.

## После merge — чистый Git
- GitHub удаляет исходную remote-ветку после squash-merge автоматически.
- `git fetch --prune origin` удаляет устаревшие remote-tracking ссылки, но не локальные ветки и не работу людей.
- Смёрженная ветка больше не используется: `git switch main`, `git pull --ff-only`, новая задача — новая ветка.
- `git branch -d <своя-ветка>` после проверки PR. После squash `-d` может отказать: `-D` только после проверки `merged=true`, отсутствия новых коммитов и явного согласия владельца.
- Незавершённую свою ветку: rebase на свежий `origin/main`; при опубликованной ветке пушить только `--force-with-lease` и только если никто другой не работает в ней.
- Worktree удалять только при чистом `git status --porcelain` и завершённой задаче; без `--force`. Общие ветки, чужие ветки, незакоммиченные файлы не удалять.
- Не делай массовое удаление через `branch --merged | xargs` и никогда не `reset --hard`. Полный регламент: `docs/WORKFLOW.md §9`.

## 6. Отчёт человеку
Коротко: что сделано (ID), как проверить, что осталось/риски, что нового узнал (допиши строку в `docs/MEMORY.md`).

## Никогда
- Не пушь в `main`, не делай force push в чужие ветки, не меняй применённые миграции.
- Не коммить секреты, датасет организаторов, `.env`.
- Не добавляй зависимость без точной версии и проверки лицензии (allowlist в `AGENTS.md`).
- Не вызывай ИИ-провайдеров напрямую — только `AiGateway` / `ai_gateway`.
- Не считай деньги во float. Не считай прогноз на клиенте.

## Приоритет инструкций
`AGENTS.md` → `zapas-dev` → скилл зоны (`backend-spring`, `forecast-ml`, `frontend-react`, `android-compose`, `devops-caddy`, `contracts-first`, `security-fintech`, `jev-typesafe`) → сторонние скиллы (animate, shadcn, springboot-security, …). При конфликте выигрывает более ранний.
